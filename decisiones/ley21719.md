## 8. Protocolo de Validación Obligatorio

Cada tarea del plan debe completar **obligatoriamente los 3 pasos siguientes** antes de marcarse como `[X]`. Sin excepción.

### Paso T — Test (TDD con Playwright)

Escribir el test **antes** de tocar cualquier código de implementación.

| Elemento | Descripción |
|----------|-------------|
| Framework | Playwright (Java/JS, según el stack del proyecto) |
| Qué prueba | La funcionalidad completa desde la perspectiva del usuario |
| Escenario mínimo | Autenticar → Navegar a la página → Interactuar con el botón/formulario → Verificar respuesta HTTP esperada (200/201/204) |
| Cobertura requerida | Happy path + al menos 1 caso de error (ej: datos inválidos, sin permisos) |
| Assert clave | El test debe fallar si la funcionalidad no está implementada |

**Formato:** El test se guarda en `src/test/playwright/{modulo}/{nombre-test}.spec.{ts,js}`.

### Paso I — Implementación Completa (Real, sin placeholders)

Implementar el flujo completo de punta a punta. **No se permiten mocks, placeholders, stubs ni `TODO` comments** en la lógica de negocio.

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│  Frontend   │ ──▶ │  Controller  │ ──▶ │   Service   │ ──▶ │  Repository  │ ──▶ │  Database   │
│ (Thymeleaf  │     │  (REST API)  │     │ (lógica de  │     │   (Spring    │     │ (PostgreSQL │
│  + HTMX)    │     │              │     │  negocio)   │     │   Data JPA)  │     │  vía Flyway)│
│ onclick ──▶ │     │ @PostMapping │     │ @Transactional│   │ save()       │     │ migración   │
│ hx-post ──▶ │     │ @RequestBody │     │ reglas +     │     │ findBy...()  │     │ ya aplicada │
│             │     │ @PreAuthorize│     │ validaciones │     │              │     │             │
└─────────────┘     └──────────────┘     └─────────────┘     └──────────────┘     └─────────────┘
```

**Checklist de implementación:**

- [ ] Migración Flyway escrita y aplicada (SQL real)
- [ ] Entidad JPA mapeada (si aplica)
- [ ] Repositorio creado (si aplica)
- [ ] Servicio con lógica de negocio real
- [ ] Controlador con endpoint real
- [ ] Template HTML con botón/formulario real
- [ ] `@PreAuthorize` con permiso granular (hasAuthority)
- [ ] Auditoría del evento (AuditLogger.log())
- [ ] Compilación: `mvn compile -q` sin errores

### Paso V — Validación de Persistencia

El test final debe **consultar el estado resultante en la base de datos** para confirmar que el dato se escribió correctamente.

| Técnica | Cómo se aplica |
|---------|---------------|
| **Vía API** | Llamar al endpoint GET correspondiente y verificar que el recurso creado/modificado/eliminado se refleja en la respuesta JSON |
| **Vía BD directa** | Ejecutar `SELECT` contra la tabla real usando `JdbcTemplate` o conexión nativa y verificar que las columnas esperadas tienen los valores correctos |
| **Caso DELETE** | Verificar que el soft-delete se aplicó (`deleted_at IS NOT NULL`), no que el registro desapareció |
| **Caso anonimización** | Verificar que los campos PII fueron reemplazados por valores anónimos (ej: email = `anon-*@deleted.local`) |

**Formato:** El test de validación se escribe como un test de integración Spring Boot (`@SpringBootTest` + `@Autowired JdbcTemplate`) que:
1. Ejecuta el escenario completo vía API REST
2. Consulta la BD directamente
3. Assert sobre los valores persistidos

### Resumen del protocolo (formato en el plan)

Cada tarea en los pilares 1-4 está marcada con `(T+I+V)`. Esto significa:

```
[T] — Test Playwright escrito y ejecutado antes de implementar
[I] — Implementación completa Frontend → Controller → Service → Repository → BD
[V] — Validación de persistencia: consulta directa a la BD confirma que el dato se escribió
```
